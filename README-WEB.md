# LinkRadar — история веб-версии 1.2.1

Актуальные инструкции настольного приложения находятся в [README.md](README.md). Этот документ описывает прежний веб-интерфейс.

Локальное приложение для диагностики стабильности сети перед трансляциями и соревнованиями программистов. Измерения настоящие: системный ICMP ping и TCP-соединения. Интерфейс открывается в браузере, сбор выполняет Python на том же компьютере. Облачный сервис не нужен.

## Анализ RTMP-трансляции

На основном экране укажите сервер приёма и нажмите «Пуск»: новая сессия проверяет ICMP и доступность TCP-порта. Можно вставить RTMP/RTMPS URL; сохраняются только хост и порт, путь и stream key отбрасываются. По умолчанию RTMP использует 1935, RTMPS — 443; фактический порт уточните у сервиса. TCP-проверка не выполняет TLS/RTMP handshake.

Профиль раскрывается одним нажатием: 1080p25/30/50/60, видео 8 Мбит/с, аудио 160 кбит/с. Показываются сглаженный jitter ICMP, средний ΔRTT, максимальный RTT и P95, серия сбоев, отсутствие ICMP-ответов и успешность подключения к порту. Отсутствие ответа промежуточного узла не считается потерей видеопотока.

Отдачу до сервера, сетевые dropped frames и переподключения внесите вручную по отдельному тесту и статистике OBS/vMix. Ориентир запаса — 1,5–2× суммы видео и аудио: для текущего профиля 12,24–16,32 Мбит/с. Это практический ориентир, не измеренная полоса и не гарантия. FPS сам по себе не задаёт допустимый jitter RTMP.

Панель объясняет сигналы риска; после минимум 20 проб обоих типов без обнаруженных сбоев показывает только результат сетевых проб. Для подтверждения качества нужна реальная трансляция. Профиль сохраняется в этом браузере; ручные наблюдения привязаны к сессии и пока не включаются в серверные экспорты. Уже запущенная ICMP-сессия продолжается без изменения; TCP появится после следующего запуска. Wireshark временно скрыт из интерфейса.

## Запуск

Нужен **Python 3.9 или новее** из [python.org](https://www.python.org/downloads/). Внешних Python-пакетов и npm-зависимостей нет. Это исходная переносимая версия, не готовый подписанный установщик EXE/DMG.

- **Windows 10/11:** распакуйте папку, запустите `Start LinkRadar.bat`. При установке Python включите launcher или добавление Python в PATH.
- **macOS:** откройте `Start Network Watch.command`. Если после распаковки нет права исполнения, выполните в Terminal `chmod +x "Start Network Watch.command"` в папке приложения.
- **Из терминала на обеих системах:** `python3 server.py` (Windows: `py -3 server.py`).

Откроется **http://127.0.0.1:8765**. Если браузер не открылся автоматически, перейдите по этому адресу. Окно терминала должно оставаться открытым. Для завершения приложения нажмите Ctrl+C. Закрытие вкладки не останавливает сбор.

Дополнительные параметры: `--port 8766`, `--no-browser`, `--data-dir /path/to/storage`. Второй процесс не может использовать ту же папку данных. Интерфейс слушает только loopback, сетевой доступ другим компьютерам не предоставляется.

## Что работает

- До 12 целей одновременно, профили «Трансляция», «Соревнование», «Свой профиль».
- ICMP IPv4/IPv6: RTT, доля отсутствующих ответов, серии сбоев.
- TCP IPv4/IPv6: время установки соединения на выбранный порт; отказ порта и таймаут сохраняются отдельно. IPv6 задаётся без квадратных скобок.
- Средняя, минимальная, максимальная задержка, P95, jitter соседних успешных измерений.
- График за 5/15 минут, час или сутки; выбор цели, порог задержки, отметки ошибок/сбоев.
- Автоматическая остановка по заданной длительности; ручная остановка.
- Оценка по обязательным целям; справочные цели не влияют на общий результат.
- График traceroute: порядок узлов, IP, полосы RTT до каждого отвечающего узла, выделение конечной цели и отдельные отметки отсутствия ответов. График использует последнюю трассировку выбранной цели.
- Режим «Маршрут»: непрерывные ICMP-трассировки IPv4/IPv6, история RTT и отсутствующих ответов каждого измеренного hop, таблица min/avg/max/jitter, выбор узла для графика. Изменившиеся IP узлов хранятся раздельно. Разовая ICMP-трассировка остаётся доступна для остальных режимов.
- Выбор семейства адресов и фиксированного IP из ответа DNS. При автоматическом выборе используется системный резолвер.
- Общий исторический фокус: поле «До» задаёт конец окна для графика, таблицы узлов и снимка маршрута. Кнопка «Сейчас» возвращает последний период.
- Wireshark: локальный импорт PCAP/PCAPNG, display filter, протоколы, пары IP, таблица пакетов, TCP retransmissions, Duplicate ACK, RST и средний ACK RTT. Опциональный короткий захват выбранного IP через dumpcap.
- Журнал отсутствия ответов, восстановления, высоких задержек; ручные отметки событий.
- Локальная SQLite-история, открытие предыдущих сессий после перезапуска.
- CSV конечных целей и отдельный CSV узлов, JSON с исходными измерениями/узлами/событиями/маршрутами, автономный HTML-отчёт. HTML можно открыть отдельно и распечатать в PDF средствами браузера.
- Сбор продолжает работать при закрытии вкладки. Приложение не установлено как системная служба и не запускается автоматически.

## Экран по образцу PingPlotter

В версии 1.2 основной экран перестроен по присланному пользователем изображению: вкладки целей и «Все цели», строка адреса, таблица `Hop / Count / IP / Name / Avg / Min / Cur / PL%`, справа диапазон Min–Max, красная линия средних RTT и голубые маркеры последних ответов. Зелёная/жёлтая/красная шкала использует границы 100 и 200 мс для визуального сравнения; согласованные пороги оценки по-прежнему задаются отдельно в настройках сессии.

Нажмите узел для его истории. Нижний график показывает RTT белой линией, отсутствующие ответы красными отметками и ошибки выполнения синими. Полоса ΔRTT показывает абсолютное изменение соседних успешных ответов, а не неизвестную нам внутреннюю формулу jitter коммерческого PingPlotter. При прореживании графика это изменение соседних отображаемых точек, с отдельной пометкой. Время до начала сбора затемнено и не заполнено нулевыми задержками.

Колесо мыши над графиком меняет окно от минуты до суток. Протяните мышью по графику, чтобы выбрать конец временного фокуса и период (минимум одна минута). Можно также задать поле «До» и список периодов. Кнопка «Сейчас» возвращает последний период. При смене сессии старый фокус сбрасывается.

Кнопка `Ⅱ` приостанавливает сбор после текущей пробы/цикла, `▶` продолжает. Таймер длительности сессии идёт и на паузе; пропуски остаются пропусками и могут исключить положительную оценку покрытия. Завершённую сессию возобновить нельзя: создайте новую. Настройка интервала от 0,5 с не гарантирует такую частоту для медленной последовательной трассировки; фактический интервал выбранного узла подписан под графиком.

Имена узлов получают через системный reverse DNS в фоне; пока PTR не разрешён или не найден, Name может совпадать с IP. В разовом снимке нет исторической статистики промежуточных узлов: Count/Avg/Min/PL% показаны прочерками. Новые ICMP-сессии автоматически собирают историю маршрута; режим «Маршрут» также остаётся доступен. Вкладка «Все цели» показывает статистику целей за всю сессию. Отчёты, журнал и оценка находятся в раскрывающемся разделе под графиком. История и Wireshark доступны в верхней панели.

Это воспроизведение основных рабочих сценариев и компоновки, не полная копия PingPlotter Pro: нет параллельного raw-ICMP движка, многооконного графика нескольких узлов, правил уведомлений и полного набора настроек оригинала.

## Маршрут и Wireshark

Для графиков PingPlotter достаточно режима **ICMP**: ping конечной цели и повторяющийся ICMP-traceroute запускаются вместе автоматически. Выберите IPv4/IPv6, лимит узлов и интервал маршрута (по умолчанию 2,5 с). Режим **«Маршрут»** также доступен: в нём конечная цель измеряется только внутри трассировки. Нажмите на строку узла: верхний график покажет его историю. Таблица узлов показывает статистику общего выбранного окна; таблица целей и общий вердикт — за всю сессию. Значение «100% нет ответа» у молчащего роутера означает отсутствие ответа на TTL-зонды и не ухудшает оценку конечной цели.

Циклы выполняются системными `traceroute -I` / `traceroute6 -I` на macOS и `tracert` на Windows. **Зонды по всем TTL не отправляются одновременно**: если цикл занимает дольше заданного интервала, следующий начинается после его завершения. Указан фактический медианный интервал выбранного узла. В Windows один замер узла — среднее доступных ответов трёх зондов tracert; процент отсутствия ответа относится к циклам без единого RTT, а не к каждому из трёх пакетов. Временные метки фиксируют получение строки от утилиты. Если цель не достигнута, отсутствие её измерения показано ошибкой, а не придуманной потерей пакета. Для самостоятельной оценки цели добавьте отдельный **ICMP** или **TCP**. Покрытие для общей оценки проверяется относительно запрошенного интервала; медленный маршрут может дать «Недостаточно данных».

Для анализа пакетов отдельно установите [Wireshark](https://www.wireshark.org/download.html) с **TShark** и **dumpcap**. На macOS приложение обнаруживает инструменты в `/Applications/Wireshark.app/Contents/MacOS`, на Windows — в PATH или `C:/Program Files/Wireshark`. Без Wireshark остальные проверки продолжают работать.

Откройте «Wireshark / PCAP», выберите файл и нажмите «Импортировать / анализировать». Примеры display filter: `udp`, `tcp`, `tcp.analysis.retransmission`, `tcp.flags.reset == 1`, `ip.addr == 192.0.2.1`. Фильтр передаётся аргументом TShark, без shell. Анализ ограничен первыми 100 000 пакетами файла; таблица — первыми 300 подходящими пакетами. ACK RTT определяется только при наличии подходящих TCP ACK. Распределение протоколов использует выбранный фильтр. «Соединения» сгруппированы по паре IP и протоколу, без разделения TCP-портов/потоков.

Для нового захвата раскройте раздел, получите интерфейсы, выберите интерфейс и буквальный IP, задайте 5–60 секунд и нажмите **«Начать захват»**. Захват ограничен этим IP, 128 байтами на пакет и 32 МБ. Даже первые байты могут содержать данные приложения. Нужны штатные права Wireshark на захват: Npcap на Windows / настройка доступа к BPF на macOS. Приложение не меняет права ОС. В этой версии захват заканчивается по таймеру/размеру; ручной досрочной остановки нет. В проверке разработки живой пользовательский трафик не захватывался.

Файлы сохраняются в `data/captures/`, автоматически не удаляются. Анализ не отправляет их в облако и не показывает payload. Повторные передачи TCP, Duplicate ACK и «previous segment not captured» — признаки, требующие анализа причин; это не точный процент сетевых потерь. Наблюдаемый битрейт не измеряет доступную пропускную способность. Полный интерфейс Wireshark, Follow TCP Stream и глубокий просмотр полей пакета остаются в самой Wireshark.

## Как проверить площадку

1. Подключите компьютер к тому интерфейсу, который будет использоваться на событии. Приложение использует системную маршрутизацию, не меняет её и не выбирает VLAN.
2. Создайте проверку с названием площадки и события.
3. Укажите реальный локальный шлюз как ICMP-цель. Адрес найдите в сетевых настройках ОС.
4. Добавьте адрес назначения трансляции или сервера соревнования. Указывайте **имя хоста/IP, без URL, пути и stream key**. Для TCP выберите фактический порт: 443 для HTTPS, 1935 только если используется RTMP на этом порту, 443 для RTMPS только если так настроен сервис. Подставленный порт нужно проверить.
5. При необходимости добавьте независимую внешнюю цель и резервное направление.
6. Выполняйте проверку минимум 15–30 минут; перед важным событием дольше. Проверяйте также под реальной нагрузкой и во время репетиции.
7. Добавляйте отметки: начало трансляции, массовая отправка решений, переключение канала, жалоба пользователя.
8. Сохраните HTML-отчёт и CSV/JSON. Они содержат проверенные адреса, периоды и параметры.

Начальные пороги: неуспешные проверки ≤0,5%, P95 ≤100 мс для трансляции / ≤150 мс для соревнования, jitter ≤20 мс, серия неуспешных ≤2. **Это стартовые ориентиры, не утверждённый SLA и не универсальный норматив.** Настройте их для маршрута, приложения и требований события.

## Как считается оценка

Положительная оценка «В порогах» возможна только когда:

- прошёл весь выбранный период;
- есть минимум 20 выполненных сетевых проверок;
- покрытие времени измерениями ≥90% относительно заданного интервала;
- нет ошибок выполнения DNS/ОС;
- нет промежутков между измерениями или по краям записи больше `3 × интервал + 2 секунды`;
- все показатели обязательной цели в заданных порогах;
- есть достаточно успешных соседних ответов для jitter.

Превышение порога даёт «Есть риск», даже если период пока короткий. Ошибки/неполный период дают «Недостаточно данных». После аварийного выхода предыдущая активная сессия маркируется как «Прервана», автоматически не возобновляется и не может стать положительной.

Доля неуспешных = число таймаутов/отказов ÷ число выполненных сетевых проверок. Ошибки DNS, отсутствие утилиты, запрет ОС **не считаются сетевыми потерями** и показаны отдельно. Для TCP этот показатель — доля неуспешных соединений, а не доля потерянных IP-пакетов.

P95 — метод ближайшего ранга. Jitter — средняя абсолютная разница задержки соседних успешных измерений; через пропуски разница не считается. Это не RTP-jitter из статистики видеосвязи. Ответ Windows `<1ms` сохраняется как верхняя граница **1 мс**, с отметкой в исходных данных.

Общая статистика относится ко всей сессии. График и его нижняя статистика — к выбранному окну. Для длинных записей график прореживается максимум до 900 точек на цель, отдавая приоритет сбоям и пикам; CSV/JSON сохраняют каждое исходное измерение.

## Ограничения

- Успешный TCP connect не проверяет TLS, HTTP, загрузку страницы, авторизацию, RTMP-публикацию или систему проверки решений.
- ICMP может фильтроваться при нормальной работе приложения. Неответивший промежуточный узел не доказывает неисправность.
- Пропускная способность, UDP/SRT/RTP, радиоэфир Wi-Fi, качество видеопотока и CPU приложением не измеряются. Для исходящей полосы нужен отдельный тест или статистика реального вещания. Хороший ping не подтверждает достаточную полосу.
- Каждый цикл трассировки отражает отдельный момент и может идти иначе, чем TCP или медиапоток. RTT включает обратный путь.
- DNS выполняется системным резолвером; без фиксированного IP в ICMP/TCP адрес обновляется ориентировочно раз в минуту, в маршруте — каждый цикл. Не измеряются все адреса CDN одновременно. Системный DNS может ждать дольше таймаута сетевой пробы; недостаточное покрытие будет видно в оценке.
- Сон, выключение и остановка процесса прерывают сбор. При старте и после пробуждения возможна необходимость новой полной проверки.
- История хранится локально в `data/network.sqlite3`. Автоматического удаления нет: следите за свободным местом, архивируйте сессии. До резервного копирования папки data остановите приложение.
- Windows-код проверен тестами команд и локализованного вывода; реальный запуск на Windows в этой сессии не выполнялся. Редкие языки вывода ping могут потребовать расширения парсера: приложение показывает ошибку, не придумывает задержку.

## Проверка разработки

```sh
python3 -m unittest discover -s tests -v
```

Сетевые пробы требуют обычного разрешения ОС на сеть. На macOS использована системная ping; TCP не требует прав администратора. При запрете ICMP приложение покажет отдельную ошибку.

## Исправление 1.2.1: ping и маршрут собираются вместе

Для каждой ICMP-цели автоматически запускается фоновый цикл traceroute с накоплением отдельных измерений узлов. Avg/Min/Max/PL%, красная кривая средних значений и полосы Min–Max вычисляются по реально собранным ответам в выбранном фокусе. Конечная строка использует основные ICMP-измерения, как и график ping: ответы из трассировки не увеличивают их счётчик. Маршрут использует текущий IP основной ping-цели, чтобы DNS/CDN не направлял две проверки на разные адреса.

Кнопка «Маршрут · авто» в работающей ICMP-сессии показывает автоматический сбор. Пауза останавливает обе проверки после текущих операций. Запуск старой сессии версии до 1.2.1 не добавляет ей отсутствовавшие в прошлом измерения: они появляются только после включения обновлённого сборщика и продолжения работы. Пока сессия на паузе, новые строки/статистика маршрута не появятся. TCP-цели по-прежнему имеют разовую трассировку по запросу.

Маршрут и ping работают одновременно, но не обязаны обновляться с одинаковой частотой: последовательная трассировка может занимать несколько секунд. Интервал её узлов указан под выбранным графиком. Разрыв при обновлении остаётся в записи. Восстановление той же сессии после обновления выполняется только явным `--resume-session ID` (при необходимости `--resume-paused`); её первоначальный срок окончания и все исходные измерения сохраняются.


### Компактный интерфейс

Wireshark / PCAP временно убран из интерфейса; установленный Wireshark и сохранённые захваты остаются на компьютере. Таблица и график уплотнены. Шкала RTT автоматически подбирается по видимым ответам, доступны фиксированные 50/100/300/1000 мс. Наведение показывает время, точный RTT и соседний ΔRTT; клик закрепляет выбранный момент при обновлениях. Средний jitter за выбранное окно показан отдельно от верхней границы шкалы ΔRTT. Средний jitter рассчитывается по исходным замерам; соседний ΔRTT не строится из прорежённых точек.


Адрес сервера редактируется в верхнем поле: введите IP или имя без протокола/порта и нажмите «Применить» либо Enter. Escape отменяет правку. Перед остановкой проверяется адрес и наличие IP выбранного семейства. Смена запускает новый полный период с прежними настройками и остальными целями; старая сессия сохраняется в истории.


### Минимальный запуск — 12 октября 2026

Главный экран: сервер, интервал 0,5 / 1 / 2 секунды и одна кнопка «Пуск / Стоп». Enter работает как кнопка. Быстрый запуск создаёт одну ICMP-цель с автоматическим маршрутом, без формы настроек. Максимальный период — 24 часа либо до ручной остановки. Дополнительные режимы, история и масштаб доступны в «Настройки и история». При смене интервала во время сбора начинается новая сессия; прежняя история сохраняется. Выбор интервала до запуска сам сбор не запускает. Реальная частота при таймаутах и последовательной трассировке может быть ниже заданной.


### Сглаженный jitter — 12 октября 2026

Оранжевая кривая теперь показывает EWMA абсолютной соседней разницы RTT: J ← J + (|RTT₂ − RTT₁| − J)/16. Это сглаженная оценка колебаний ICMP RTT; она не измеряет односторонний jitter RTP. Коэффициент внутреннего движка PingPlotter не подтверждён: воспроизведено плавное поведение предоставленного графика, не заявлена побитовая идентичность. Средний ΔRTT за окно остаётся отдельной статистикой. Курсор показывает исходный RTT, отдельный ΔRTT и сглаженный jitter выбранного замера.

Расчёт выполняется сервером до прореживания графика. До начала видимого окна берутся 256 предшествующих замеров для прогрева EWMA. Потери, ошибки, смена IP и разрывы сбора прекращают цепочку; несуществующие пары не создаются. Ориентир — пунктир 35 мс; шкала не менее 0–50 мс с расширением при больших значениях.


Читаемый итог RTMP: четыре состояния с текстом и символами — сетевые проверки в порядке, нужно проверить, проблемы для эфира, недостаточно данных. Красный означает указанные сетевые пропуски/переподключения либо отдачу ниже суммы битрейтов; жёлтый — сигналы сетевых проверок или недостаточный запас. Зелёный подтверждает только ICMP/TCP без сбоев при минимум 20 пробах каждого типа. Недостающая отдача и статистика OBS/vMix явно перечислены даже при зелёном сетевом результате. Jitter не получает произвольного порога пригодности RTMP. Карточки поясняют значения, итог относится к окну графика; общий пороговый статус убран из подписи графика во избежание противоречия.



Минимальный экран RTMP: оставлены адрес/интервал/пуск, итог с одной строкой причины, jitter, ping без ответа, доступность TCP-порта и графики. Маршрут свёрнут в details, профиль и журнал доступны по раскрытию. Убраны повторные пояснения и длинная статистика; курсор сохраняет время, точный RTT и jitter. В браузере проверены текущий сбор и раскрытие/сворачивание маршрута. JS синтаксис и тесты анализа RTMP прошли.

По пользовательскому скриншоту скрыта только строка route-focus под таблицей; маршрут и узлы сохранены. Журнал событий очищается при Store startup и Monitor.start; замеры сохраняются. Проверены 28 unit и 5 API-интеграционных тестов, после перезапуска основной базы events=0. Закрытие вкладки не завершает сервер.

Светлый вариант отменён пользователем; восстановлен прежний тёмный интерфейс.

### LLDP и скорость — 13 октября 2026

В нативном приложении сверху отображаются Switch / Port / VLAN (PVID), MAC / IP / MASK / GATEWAY / DNS. Сбор начинается автоматически при открытии окна. LLDP использует системную libpcap на Mac и Npcap на Windows; Wireshark не нужен. Если объявления, PVID или права захвата отсутствуют, показывается причина и «—» вместо предположений. macOS иногда скрывает текущий MAC; тогда используется доступный аппаратный адрес с пояснением в подсказке либо «—».

«Измерить скорость» выполняет реальную загрузку и отдачу через Яндекс CDN, с отменой и обозначением нагрузки на графике. Замер запускается только кнопкой, около 8 секунд на направление. Подробности метода и ограничения: STANDALONE.md. Зависимости для разработки: `pip install -r requirements-desktop.txt`; в готовых пакетах Python/Qt/certifi включены.
